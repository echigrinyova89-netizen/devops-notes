### MAC (Mandatory Access Control)

Обычные права в Linux - это примерно: владелец/группа/остальные

И владелец файла во многих случаях может менять доступ

А MAC работает иначе: права определяяются централизованной политикой безопасности и пользователь сам не может просто решить - "я теперь разрешаю этому процессу доступ сюда"

То есть это выглядит так:
- DAC / chmod / ACL - владелец файла может управлять доступом
- MAC - сверху политика безопасности, она может сказать нет, даже если вроде как права Linux разрешают

То есть у файла могут быть права -rw-rw-rw-, но AppArmor может все равно сказать процессу, что тебе нельзя писать в этот файл

В Linux есть 2 известных механизма MAC:
1. AppArmor
2. SELinix

1. AppArmor ограничивает конкретные приложения с помощью профилей.
Например, у нас есть программа btm и мы можем создать правило:

она может:
- читать /proc
- читать определенные файлы

но не может:
- читать некоторые конфиги
- обращаться куда-то еще

То есть AppArmor как бы пишет политику для приложение, например, вот тебе это можно, а все остальное нет - согласно политике

У профиля в таком случае может быть 2 режима:
1. complain - приложение нарушает политику, но AppArmor его не блокирует, а записывает в лог. И мы можем в таком случае посмотреть, что приложению реально надо. 
2. enforce - приложение нарушает политику и AppArmor его блокирует.

То есть в первом варианте мы наблюдаем, а во втором реально защищаем.

Просмотреть текущие профили можно с помощью:
sudo apparmor_status

Профиль в AppArmor - это просто файл с правилами для конкретной программы.

2. SELinux - это тоже механизм MAC, но логика у него воспринимается сложнее.

Он использует политики безопасности и контексты безопасности, которые назначаются файлам процесса и портам. Именно эти контексты опеределяют, что кому разрешено делать.

Проще всего представить так:
AppArmor - смотрит на профили конкретных приложений
SELinux - смотрит на метки объектов и правила взаимодействия между ними

Например: есть процесс Caddy, файл и порт 2019
У каждого из них может быть свой security context

Формат security context in Linux:
user:role:type:level

Например: system_u:object_r:bin_t:s0

1. Самое важное поле для начала - type 
процесс имеет type A
файл имеет type B
порт имеет type C

Политика SELinux говорит:
может ли type A 
читать type B
писать type B
подключаться к type C

То есть это происходит так SELinux принимает решение: процесс хочет выполнить действие - SELinux смотрит его контекст - смотрит контекст ресурса - сверяется с политикой - разрешает или не разрешает 

***Очень важные момент: SELinux может запретить действие даже тогда, когда обычные права DAC разрешают, и при конфликте SELinux возьмет приоритет***

У SELinux есть 3 режима:
- enforcing - правила применяются и нарушения блокируются 
- permissive - нарушения не блокируются, только логируются
- disabled - SELinux выключен

Именно поэтому при настройке часто используют режим permissive, чтобы не сломать сервис

Переключение:
- setenforce 1 -> enforcing
- setenforce 0 -> permissive

Чтобы посмотреть список портов и пользователей под управлением SELinux используйте команду:

sudo semansge port -l
sudo semanage user -l

Если к командам ps, mkdir, id, cp netstat и тд - добавить флаг -Z, то он покажет нам security context для каждого объекта.

Unconfined - означает, что контекст неограничен
